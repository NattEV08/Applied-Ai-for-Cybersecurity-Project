# Case and team integration contract

Scenario: A fictitious mid-sized retailer, Northstar Retail, runs an e-commerce backend, POS management service and low-criticality training application. Source code repositories are scanned by **Bandit** (Python SAST) and **Trivy** (dependency SCA), with results joined to asset and stakeholder records in local SQLite. A deterministic risk scorer prioritizes findings; a local Ollama model produces reviewable risk explanations and proposed mitigation steps.

## Acceptance criteria for Week 8 proposal
1. Problem statement & operational scenario tied to code and dependencies.
2. Local architecture diagram with data flows and trust boundaries.
3. Four feature responsibilities, owners, deliverables and integration contract.
4. Layered security controls: app (input validation, auth planned, output encoding), data (local SQLite access limits, secrets policy, at-rest encryption proposed), system/network (loopback binding, no untrusted code execution, network restrictions).
5. Evaluation approach: extraction precision on fixture cases; asset attribution, priority reproducibility, LLM groundedness and prompt injection robustness.
6. Distinguish SAST CWE findings from SCA CVE findings. Do not call project CVSS generated by the AI.

## Example lifecycle
1. Authorized analyst selects one source repository mapped to `AST-ECOM`.
2. SAST -> JSON CWEs; SCA -> JSON CVEs; findings normalized.
3. SQLite stores raw evidence and business ownership/exposure.
4. Deterministic risk engine derives score, category and rationale.
5. Local LLM drafts explanation and remediation suggestions from fixed, grounded evidence.
6. Human reviewer approves action and verifies rescanning after changes.

## Roles and milestones
- Member 1 SAST: Bandit wrapper, parser, tests, result provenance.
- Member 2 SCA: Trivy install, fs scan, parser, CVE/versions/fix metadata, tests.
- Member 3 AI/DB: schema, deterministic risk score, Ollama structured output, guardrails.
- Member 4 UI/security: local Flask read-only dashboard, input/output validation, authentication design, three-layer security validation coordination.

Everyone documents one defense-in-depth control in their own module, and Member 4 coordinates the integrated demonstration.
